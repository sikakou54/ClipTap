# FAILの原因分類

ランナーは検証ステップの失敗を `REQUIRES_TRIAGE`、操作ステップの失敗を `AUTOMATION_ERROR` として置く。
これは仮置きであり、**そのまま最終結果にしてはいけない**。
統括が次の順で確認し、6分類のいずれかへ確定して `results-tests.csv` の `FailureClass` を書き換える。

## 確認の順序

上から順に潰す。テスト側の誤りを先に否定しないと、アプリの不具合を誤検出する。

```
1. テスト仕様の誤り        → TEST_SPEC_ERROR
2. 前提条件の誤り          → PRECONDITION_ERROR
3. 自動化処理の誤り        → AUTOMATION_ERROR
4. 環境の問題              → ENVIRONMENT_ERROR
5. 仕様と実装の不一致      → SPEC_IMPLEMENTATION_MISMATCH
6. アプリの不具合          → APPLICATION_DEFECT
```

## 各分類の判断基準

### TEST_SPEC_ERROR — テスト仕様の誤り

- 期待値が機能仕様書と食い違っている（仕様書を読み違えた）
- 手順が実際のUIと合っていない（存在しないボタンを押そうとしている）
- 前提条件で作った状態と `TestData` の説明が矛盾している
- ステップの順序が実際の操作順と違う

確認方法: 機能仕様書の該当節と、`screens.csv` のSignature、AXダンプを突き合わせる。

対応: テスト仕様書を直して再実行する。不具合登録はしない。

### PRECONDITION_ERROR — 前提条件の誤り

- fixtureが意図した状態を作れていない（`state.sh schema` で件数を確認する）
- プランや並べ替えの設定が反映されていない（アプリ再起動を挟んでいない）
- 前のテストのCleanupが漏れて状態を引きずっている

確認方法: 失敗時に残る `<TestID>-<StepNo>-FAIL.txt` の先頭にある Expected / Actual と、
`state.sh sql` でDBの実際の中身を照合する。

対応: fixtureまたは `Precondition` を直して再実行する。不具合登録はしない。

### AUTOMATION_ERROR — 自動化処理の誤り

- ロケータが要素を特定できていない（ラベルが変わった、`visible=true` が無い）
- 要素が広告バナーに覆われていてタップが届いていない
- 待ち時間が足りず、画面が出る前に検証している
- Expoのdev-menuやDevToolsのインスペクタが画面を覆っている

確認方法: 失敗時のスクリーンショットとAXダンプを見る。
「操作は成功しているが結果が違う」のか「そもそも押せていない」のかを見分ける。
`sim.sh dump` を手で実行して同じ手順を再現すると早い。

対応: ロケータ・待ち・スクロールを直して再実行する。不具合登録はしない。
ただし「ラベルが無いためにテストできない」が繰り返し起きる箇所は、
アクセシビリティ上の課題として別途記録する価値がある。

### ENVIRONMENT_ERROR — 環境の問題

- シミュレータが起動していない、アプリが未インストール
- アクセシビリティ権限が未許可
- `ALLOW_NETWORK_TOGGLE=0` のためネットワーク切替ができない
- Metroが落ちている、ビルドが古い

対応: 環境を直して再実行する。結果は `BLOCKED` のままにしておき、PASSへ書き換えない。

### SPEC_IMPLEMENTATION_MISMATCH — 仕様と実装の不一致

実装は一貫して動いているが、機能仕様書の記述と違う。

- 機能仕様書に「Aになる」と書いてあり、実装は一貫して「B」になる
- どちらが正しいかをこのスキルでは決めない

対応: **不具合管理台帳へ登録する。**
`仕様根拠` に機能仕様書の節番号と該当文を引用し、
`実際結果` に実装の動作を書く。両方を確認できる状態にして残す。
アプリも仕様書も勝手に直さない。

### APPLICATION_DEFECT — アプリの不具合

機能仕様書に照らして、実装が誤っている。

- 仕様どおりの操作で処理が完了しない
- クラッシュ・データ消失・表示とコピー結果の食い違い
- 仕様に書かれた条件分岐が実装されていない

対応: **不具合管理台帳へ登録する。** アプリは修正しない。

---

## 判断に迷ったとき

### 「アプリの不具合」と「仕様と実装の不一致」の見分け

機能仕様書に**明示的な記述があるか**で分ける。

- 記述があり、実装がそれと違う → まず `SPEC_IMPLEMENTATION_MISMATCH`
  - ただし、クラッシュ・データ消失・セキュリティ上の問題は記述の有無に関わらず `APPLICATION_DEFECT`
- 記述が無く、期待値をClaudeが推測して書いていた → `TEST_SPEC_ERROR`
  - 推測で仕様を足してはいけない。機能仕様書§1.1に従いソースコードを正として仕様書側を実装へ合わせる。実装からも判断できない差はユーザーへ確認する

### 再実行でPASSしたとき

**最初のFAILを無効化してはいけない。**

- `再現性` を `Intermittent` として不具合登録する
- 複数回実行して再現率を記録する
- 「もう一度やったら通ったので問題なし」とは書かない

タイミング依存のFAILは、待ち不足（`AUTOMATION_ERROR`）と
アプリ側の競合状態（`APPLICATION_DEFECT`）の両方があり得る。
待ちを十分に伸ばしても再現するなら後者を疑う。

## 分類の記録

`results-tests.csv` の `FailureClass` を書き換え、
`APPLICATION_DEFECT` と `SPEC_IMPLEMENTATION_MISMATCH` には `BugID` を入れる。

```bash
# 登録漏れ・分類漏れの検出
node .claude/skills/full-test/scripts/bug.mjs check --run <runId>
```

`REQUIRES_TRIAGE` が1件でも残っている状態でレポートを確定してはいけない。

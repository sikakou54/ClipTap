# 工程とエージェント構成

テスト仕様書は「作る人」と「見る人」を分けないと網羅性が担保できない。
同じ思考で書いた本人が同じ思考で見直しても、抜けている観点は抜けたままになる。

## 4つの役割

| 役割 | 立場 | 責務 |
|---|---|---|
| 統括 | システムスペシャリスト | 全工程の統括、対象範囲の確定、成果物の統合、トレーサビリティの管理、完了判定 |
| 前提条件確定 | テスト環境担当 | 全テストの前提条件を実行可能な形へ確定する。不明点を残さない |
| 仕様書作成 | ベテランSE | 機能→条件→パターン→テストケースへの展開 |
| レビュー | ベテランSE（作成者と独立） | 網羅性・一意性・客観性の点検と差し戻し |

Claude Code上では、この4役をサブエージェントとして並行に走らせるか、
1つのセッションで役割を切り替えて実行する。どちらでも構わないが、
**レビューは必ず作成の成果物だけを入力にして、作成時の思考を引き継がずに行う**こと。
作成時の判断根拠を共有すると、同じ見落としをそのまま追認する。

---

## 工程

```
1. 対象範囲の確定        統括
2. 機能仕様書の解析      統括 → features.csv
3. ソースコード解析      仕様書作成 → screens.csv / routes.csv / 条件分岐の抽出
4. パターン展開          仕様書作成 → pattern-matrix.csv
5. 前提条件の確定        前提条件確定 → Precondition列の値とfixtureの過不足
6. テストケース化        仕様書作成 → testspec.csv
7. 機械検証              validate.mjs（エラー0件になるまで戻る）
8. 独立レビュー          レビュー → 指摘0件になるまで4〜6へ戻る
9. 網羅性検証            coverage.mjs（画面・機能・パターン・Routeが100%）
10. テスト実行           run.mjs
11. 結果検証と原因分類   統括
12. 不具合登録           統括 → issues.md
13. レポート             report.mjs
```

7と9は機械が判定する。8は人（Claude）が判定する。
**7・8・9のいずれかが未達のまま10へ進んではいけない。**

## 1. 対象範囲の確定（統括）

自動実行の対象は **iOSシミュレータ上のモバイルアプリ** とする。
以下は同じテスト仕様書に載せるが、実行方法を分けて `Priority` と `Precondition` で区別する。

| 対象 | 扱い |
|---|---|
| モバイル（iOS シミュレータ） | 自動実行 |
| モバイル（iOS 実機） | 手動。拡張キーボード・触覚フィードバック・実購入はシミュレータで再現しない |
| モバイル（Android） | 手動。`RefreshControl` などiOSと実装が別 |
| Web | 対象外（別の実行基盤が必要）。ただし共有ロジック由来のパターンは記録する |
| キーボード拡張 | 手動。別バンドルでAXツリーからも操作できない |

対象外にしたものを `pattern-matrix.csv` から消してはいけない。
`Reachability=UNREACHABLE` と `UnreachableReason` に理由を書いて残す。

## 2. 機能仕様書の解析（統括）

`docs/機能仕様書.md` は §7 の機能一覧が F-01〜F-23 で、§8.N が F-N に対応する。
各節は 機能概要 / 事前条件 / 事後条件 / 機能詳細 の4区分。

`features.csv` を作る。1機能1行。

- 事前条件 → そのままテストの `Precondition` の材料になる
- 事後条件 → `PostCondition` と検証ステップの材料になる
- 機能詳細の表 → 入力制約・プラットフォーム差・条件分岐の材料になる

§9（画面仕様）、§10.4（利用者向けエラー）、§13（状態）、§14（DB）も必ず読む。
§10.4 のメッセージ文言は異常系の期待値そのものになる。

## 3. ソースコード解析（仕様書作成）

機能仕様書だけではパターンを特定しきれない。最低限、次を読む。

| 見るもの | 場所 | 取り出すもの |
|---|---|---|
| ルート定義 | `apps/mobile/app/**` と `apps/mobile/app/_layout.tsx` | 全Route、presentation（modal / transparentModal / fullScreenModal / card） |
| 画面実装 | `apps/mobile/app/**/*.tsx` | 到達経路、条件付き表示、空状態 |
| フック | `apps/mobile/src/hooks/**` | 派生状態、初期選択、useEffectの依存 |
| サービス | `packages/shared/src/services/**` | 業務ルール、バリデーション、上限判定 |
| Mapper | `packages/shared/src/mappers/**` | 実際に保存・削除される範囲 |
| 定数 | `packages/shared/src/constants/**` | 境界値（`INPUT_LIMITS` / `FEATURE_LIMITS`） |
| 文言 | `packages/shared/src/i18n/{ja,en}.json` | 期待値に使う実際の文字列 |
| 状態 | `packages/shared/src/providers/**` | 画面をまたぐ状態の保持と破棄 |

条件分岐は `if` / 三項演算子 / `switch` / `??` / `&&` の全てを対象にする。
抽出した分岐は `ConditionID` を振り、`pattern-matrix.csv` の `CodeRef` にファイルパスを残す。

**期待値の文言はi18nのJSONから取る。**画面を見て書き写すと、
実装が変わったときにテストが落ちる理由が「文言変更」なのか「不具合」なのか分からなくなる。

### 仕様と実装が食い違ったとき

どちらかを正として勝手に補正しない。

1. `pattern-matrix.csv` にパターンを2つ作る（仕様どおりの動作 / 現在の実装の動作）
2. 実装側のパターンの `Source` を `SourceCode`、仕様側を `FunctionalSpec` にする
3. テストの期待値は **機能仕様書** に合わせる
4. 実行でFAILしたら `SPEC_IMPLEMENTATION_MISMATCH` として不具合登録する

[preconditions.md](preconditions.md) を参照。
`Precondition` 列に書ける値は閉じた語彙で、`validate.mjs` が検査する。
既存のfixtureで表せない状態が出てきたら、**fixtureを追加してから**テストを書く。
「〜な状態にしておく」という散文を残してはいけない。

## 8. 独立レビュー（レビュー）

`validate.mjs` が通ったものだけをレビューへ回す。機械で分かることを人が見る必要はない。
レビューは次を見る。

- [ ] `_layout.tsx` を除く `apps/mobile/app/**` の全画面ルートファイルが `screens.csv` にあるか（ファイル一覧と突き合わせる）
- [ ] `features.csv` が F-01〜F-23 を漏れなく持つか
- [ ] 同じRouteでも、起点・条件・ユーザー状態・権限・データ状態が違えば別パターンになっているか
- [ ] 各機能に正常系だけでなく異常系・境界値があるか
- [ ] 境界値が「上限ちょうど」「上限+1」「下限ちょうど」「下限-1」で揃っているか
- [ ] Free / Pro の差があるすべての機能で両方のパターンがあるか
- [ ] データ0件・1件・複数件・上限到達の差があるすべての画面で各状態のパターンがあるか
- [ ] ソースコードの条件分岐に対応するパターンがあるか（`CodeRef` を辿って確認する）
- [ ] 手順が一意か（同じCSVを2人が実行して違う操作にならないか）
- [ ] 期待値が客観的か（機械が真偽を判定できるか）
- [ ] 前提条件が実行可能な語彙で書かれているか
- [ ] UNREACHABLE の根拠が妥当か（面倒だから除外していないか）

指摘は1件でもあれば差し戻す。指摘0件になるまで繰り返す。

## 11. 結果検証と原因分類（統括）

FAILは自動では分類しきれない。ランナーは検証ステップの失敗を `REQUIRES_TRIAGE` とし、
操作ステップの失敗を `AUTOMATION_ERROR` として置く。統括が次の順で確定する。

[failure-classification.md](failure-classification.md) を参照。

**FAILを見つけてもアプリを修正しない。** このスキルの成果物はテストと不具合台帳であり、
修正は別の作業として切り出す。
